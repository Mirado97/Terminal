## Проект: Arbitrage Terminal

Криптовалютный арбитражный терминал на Python/asyncio. Отслеживает спреды между биржами (Bybit, Binance, OKX), исполняет сделки, управляет рисками. Фронтенд — React/Next.js в `frontend/`.

### Запуск и разработка

```bash
# На сервере (Ubuntu, /opt/terminal)
git pull && python3 tui_real.py

# Тесты
pytest
pytest tests/test_spread.py          # один файл
pytest --cov=. --cov-report=term     # с покрытием

# Установка зависимостей
pip install -e ".[dev]"
```

### Окружения (APP_ENV)

| APP_ENV      | Конфиг-оверрайд                | Суффикс credentials     |
|--------------|--------------------------------|-------------------------|
| (пусто)      | `config/settings.yaml`         | `BYBIT_API_KEY`         |
| `testnet`    | + `config/testnet.yaml`        | `BYBIT_API_KEY_TESTNET` |
| `production` | + `config/production.yaml`     | `BYBIT_API_KEY`         |

`.env` читается через `SecretsManager` (`credentials/manager.py`). Шаблон: `.env.example`.  
`${POSTGRES_URL}` и `${REDIS_URL}` в `config/settings.yaml` — резолвятся из переменных окружения.

### Архитектура

```
core/           — ConfigManager, AsyncLifecycle, настройка structlog
credentials/    — SecretsManager (API-ключи по биржам)
exchanges/      — BaseExchange ABC, Bybit/Binance WS+REST, TokenBucket rate limiter
orderbook/      — LocalOrderBook (snapshot/delta), OrderBookEngine (CRC32, stale watchdog)
spread/         — FeeTable, SpreadCalculator (raw→net), SpreadDetector
execution/      — OrderManager, SmartOrderRouter, ExecutionEngine (обе ноги параллельно)
risk/           — RiskLimits, InventoryManager, RiskEngine (pre-trade, circuit breaker)
watchdog/       — WorkerSupervisor, WatchdogOrchestrator (500+ asyncio workers)
storage/        — asyncpg pool, redis.asyncio, 10 таблиц, TradeRepository и др.
backtesting/    — OrderBookReplayer, TradeSimulator, MonteCarloEngine
frontend/       — Next.js + Tailwind + Recharts, WS push от aiohttp сервера
config/         — settings.yaml + testnet.yaml + production.yaml
tests/          — 232 теста, pytest-asyncio auto mode
```

**Ключевые паттерны:**
- Все компоненты регистрируют startup/shutdown через `AsyncLifecycle.on_startup` / `on_shutdown`
- Логирование: `structlog` — консоль в dev, JSON в prod (через `json_output=True` по APP_ENV)
- Модели данных: `msgspec.Struct` — быстрая сериализация/десериализация
- Exchange WS: exponential backoff 1s→60s, stale watchdog 35с, ping loop
- Execution: SmartOrderRouter — maker если spread ≥ 20bps, иначе IOC; emergency hedge recovery

Поведенческие правила для снижения типичных ошибок LLM при написании кода.

**Компромисс:** эти правила смещают баланс в сторону осторожности, а не скорости. Для тривиальных задач руководствуйся здравым смыслом.

## 1. Сначала думай, потом кодируй

**Не предполагай. Не скрывай неопределённость. Озвучивай компромиссы.**

Перед реализацией:
- Явно формулируй допущения. Если не уверен — спроси.
- Если возможны несколько интерпретаций — предложи их, не выбирай молча.
- Если есть более простой подход — скажи об этом.
- Если что-то непонятно — остановись. Назови проблему. Спроси.

## 2. Простота прежде всего

**Минимум кода, решающего задачу. Ничего спекулятивного.**

- Никаких фич сверх запрошенного.
- Никаких абстракций для однократно используемого кода.
- Никакой «гибкости» и «конфигурируемости», которую не просили.
- Никакой обработки ошибок для невозможных сценариев.
- Написал 200 строк, а можно 50 — перепиши.

Спроси себя: «Скажет ли опытный инженер, что это переусложнено?» Если да — упрости.

## 3. Хирургические изменения

**Трогай только то, что необходимо. Убирай только свой мусор.**

При редактировании существующего кода:
- Не «улучшай» соседний код, комментарии или форматирование.
- Не рефактори то, что не сломано.
- Соответствуй существующему стилю, даже если сам сделал бы иначе.
- Заметил несвязанный мёртвый код — упомяни, но не удаляй.

Когда твои изменения создают «сироты»:
- Удаляй импорты/переменные/функции, которые ТВОИ изменения сделали неиспользуемыми.
- Не удаляй существующий мёртвый код, если не просили.

Проверка: каждая изменённая строка должна напрямую связываться с запросом пользователя.

## 4. Целеориентированное выполнение

**Определяй критерии успеха. Итерируй до проверки.**

Преобразуй задачи в проверяемые цели:
- «Добавь валидацию» → «Напиши тесты для невалидных входных данных, потом сделай так, чтобы они прошли»
- «Исправь баг» → «Напиши тест, воспроизводящий баг, потом сделай так, чтобы он прошёл»
- «Отрефактори X» → «Убедись, что тесты проходят до и после»

Для многошаговых задач — кратко опиши план:
```
1. [Шаг] → проверка: [как проверить]
2. [Шаг] → проверка: [как проверить]
3. [Шаг] → проверка: [как проверить]
```

Чёткие критерии успеха позволяют итерировать самостоятельно. Размытые («сделай так, чтобы работало») требуют постоянных уточнений.

---

**Эти правила работают, если:** в диффах меньше лишних изменений, меньше переписываний из-за переусложнения, а уточняющие вопросы задаются до реализации, а не после ошибок.
